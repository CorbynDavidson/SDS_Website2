# Data ownership, backup and recovery

Public source/media live in Git; enquiries, evidence and drafts remain private in D1/R2. No real submissions, production database dumps, credentials or personal attachments belong in this public repository or GitHub Actions artifacts.

Schema migrations are generated by Drizzle from `db/schema.ts`. `0000_futuristic_iron_man.sql` preserves the existing enquiry schema; the additive migration creates new submissions, upload metadata, rate buckets and drafts. Applied migrations/snapshots/journal entries are immutable. Check applied migration state before retrying a failed deployment; migrations can be applied before Worker upload fails.

## Rehearsal completed locally

Tests apply the actual SQL files to SQLite, preserve existing enquiries, restart the Worker against the same database, read durable submissions/drafts, validate evidence linkage and verify denied access. This does not constitute a production backup/restore rehearsal.

## Required production procedure

1. The SDS data owner identifies the live database and private evidence bucket through the hosting account. Capture a restricted export/snapshot before cutover and record its timestamp, owner and retention location privately.
2. Restore into a separate restricted rehearsal database, apply only unapplied migrations, verify counts/latest timestamps and authorised operator access. Keep evidence metadata and R2 objects together; verify a sample attachment.
3. Agree backup frequency, retention, deletion/legal hold responsibilities and who monitors failures. Keep the record of these decisions outside public Git if it contains personal or account details.
4. Export review enquiries or existing CMS leads only if SDS requests that transfer; never scrape private submissions from the public CMS. Preserve the earlier Sites enquiries in place during this release.
5. On recovery, restore compatible code and database schema together. Rollback should keep additive tables and post-release enquiries; do not drop them to make an older build appear unchanged.

The public CSV view is capped at the 500 newest new records and 500 newest legacy records. It is a convenient operator export, not a full database backup. A long-term operations interface may need pagination/filtering once actual volumes and roles are agreed.
